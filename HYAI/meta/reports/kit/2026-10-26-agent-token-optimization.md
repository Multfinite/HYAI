# Разбор применимости рекомендаций по токенам к HYAI

## Вопрос

Насколько технически оправданы переданные рекомендации по снижению расхода токенов и что из них применимо к HYAI?

## Разбор

### Краткий вывод

[В] Основа не бредовая: повторная передача длинной истории, избыточные ответы инструментов и ненужная генерация действительно могут повышать расход и задержку. Но текст смешивает контекстное окно, тарифицируемые токены, деньги, задержку и качество; заявления об экспоненциальном росте и процентах экономии не обоснованы данными, приложенными к рекомендациям.

[И] Паспорт описывает HYAI как каркас правил для агента — домены, профили и проверки (`HYAI/meta/project.md`); манифест задаёт entrypoint, конфигурацию и проверки (`HYAI/meta/manifest.yaml`). В изученных источниках нет реализации LLM-runtime, API-провайдера, кэширования запросов, роутинга моделей или оркестратора. Это исключает прямое управление тарификацией провайдера, но не структурную оптимизацию инструкций, которые агент получает из `AGENTS.md`.

[В] По локальным размерам `AGENTS.md` — 15 787 байт, 549 слов и 171 строка; общий фрагмент ядра — 8 590 байт, а четыре фрагмента доменов — суммарно 6 066 байт. Это измерения файлов, не число токенов и не прогноз цены. Сборщик `HYAI/tools/assemble_agents.py` добавляет фрагмент каждого активного домена независимо от того, какой домен нужен для текущей задачи.

### Оценка тезисов

| Тезис | Оценка | Почему / ограничение |
| --- | --- | --- |
| «Каждый шаг повторно передаёт всю историю», рост «по экспоненте» | [В] Частично верно как описание некоторых stateless API; «экспонента» некорректна для обычного добавления сообщений. Размер контекста одного шага обычно растёт примерно линейно по числу шагов, а суммарный ввод за N шагов может расти квадратично, если каждый раз отправлять всю историю. Stateful API, сокращение истории и prompt caching меняют картину и/или тарификацию. |
| Обрезка истории и tool results | [В] Полезно только при сохранении нужных фактов, ошибок, ссылок на источники и возможности дочитать исходник. Наивное усечение по символам способно удалить важный контекст и ухудшить корректность. |
| Sliding window + summary | [В] Практичный шаблон, но приведённый код демонстрационный: summary заменяется новым, а не явно объединяется с предыдущим; фиксированные последние три сообщения могут разорвать пару вызов/ответ инструмента. Нужны тесты сохранения решений, ограничений и provenance. |
| Prompt caching | [В] Потенциально снижает стоимость повторного ввода при поддержке провайдера и выполнении его условий. Не сокращает автоматически размер контекстного окна; hit rate, минимальный префикс, срок жизни и тариф зависят от API. Пример с одним beta-заголовком не универсален. |
| Сжатие system prompt, краткий JSON, жёсткий `max_tokens` | [В] Хорошие рычаги только при неизменной полноте задачи. JSON может быть многословнее свободного текста; лимит обрезает ответ, а не гарантирует экономию, если естественный ответ и так короче. Универсальный запрет на пояснения ухудшает задачи, где нужна проверяемая аргументация. |
| Дешёвая модель, иерархия агентов, speculative execution | [В] Может быть выгодно при измеренной разнице качества и цене. Дополнительная классификация, критика, синтез и повторные запросы сами стоят денег и времени; декомпозиция может дублировать контекст. Проверка ответа другой LLM не равна проверке по эталону. |
| State machine и лимиты шагов | [В] Хорошо ограничивают известный стабильный процесс, но способны преждевременно оборвать исследование или восстановление после ошибки. Нужны условия завершения, обработка сбоя и путь эскалации. |
| Кэш результатов инструментов | [В] Может сэкономить повторное выполнение детерминированного инструмента. Сам по себе кэш не сокращает токены, если сохранённый полный результат снова передаётся модели; для изменяемых данных нужны срок годности и инвалидирование. |
| TOON, RTK/Tokenade, LLMLingua | [Г] Возможная экономия зависит от токенизатора, структуры данных, качества восстановления и конкретной задачи; проценты из текста здесь не подтверждены тестом на целевом корпусе. Установка прокси/библиотек добавляет эксплуатационные, безопасностные и приватностные издержки. |
| Цены и числа экономии (−20–90%, «80/20», $/M) | [В] Это не переносимые константы: стоимость зависит от провайдера, модели, типа токена, кэширования, тарифа и даты. В переданных текстах нет воспроизводимого baseline, трасс запросов, состава задач и измерения качества, поэтому проценты не подтверждены. |
| Мониторинг токенов и стоимости | [В] Направление правильное, но пример формулы с фиксированными тарифами — иллюстрация, не актуальный калькулятор. Нужно отдельно учитывать uncached/cached input, output и иные тарифицируемые категории, если API их сообщает; сравнивать стоимость успешной задачи, качество и повторы. |

**Примечания к псевдокоду.** [В] В примере `speculative_solve` проверка `"YES" in check` может принять ответ вроде `NO — YES не подтверждено`; нужен строгий формат результата, а лучше проверяемый критерий. В примере token budget оценка `estimated` плюс `usage.total_tokens` может дважды учесть ввод, если `total_tokens` уже включает его. `len(solution) // 3` — лимит в символах, а не оценка токенов. В примере кэширования `md5` не нужен как криптографическая защита ключа и не решает проблемы устаревания данных. Это иллюстративные фрагменты, не готовая production-реализация.

### Применимость к HYAI

[И] У HYAI есть короткий entrypoint и сборка инструкций, доменные процессы, отчёты как переносимое состояние между сессиями и проверки (`HYAI/core/kernel/agents.md`, `HYAI/core/kernel/workflows/task.md`, `HYAI/meta/reports/README.md`). Это поддерживает выборочное чтение и передачу компактного состояния на уровне практики, но не управляет API-историей, tool schemas, prompt cache, модельным роутингом или `max_tokens`.

| Направление | Применимость | Практический вывод |
| --- | --- | --- |
| Минимизировать нерелевантное чтение; кратко фиксировать результат и открытые вопросы | Высокая, как рабочая рекомендация пользователю HYAI | Совместимо с текущими процессами и отчётами; не обещать конкретный процент экономии. |
| Фильтрация вывода инструментов, бюджет шагов, ограничения генерации | Частичная | Имеет смысл формулировать как советы для runtime/интеграции с явными оговорками о потере данных и проверке полноты. |
| Prompt caching, sliding-window на уровне API, роутинг, Batch API, multi-agent orchestration | Низкая на уровне самого каркаса | Реализуются в конкретном хосте/провайдере, которых HYAI не задаёт. Не превращать в обязательные правила ядра. |
| Внешние утилиты, прокси и компрессоры | Условная | Сначала benchmark и анализ данных/приватности; зависимости требуют отдельной цели и проверки. |
| Проценты экономии и универсальные тарифы | Не переносить | Требовать benchmark: модель/провайдер/версия, набор задач, baseline, качество, стоимость и задержка до/после. |

### Можно ли уменьшить расход формулировками и устройством ядра?

[В] Да. Это относится непосредственно к HYAI: каркас может управлять объёмом и релевантностью текста в точке входа, даже если не управляет API модели. Самый перспективный шаг — не «сжать всё любой ценой», а разделить контекст по моменту необходимости.

[В] Сейчас сборщик склеивает ядро, сводку активных пар и фрагменты всех четырёх активных доменов. Если после определения домена загружать только один его фрагмент, из `AGENTS.md` можно было бы убрать около 4,4–4,7 КБ исходного текста на задачу (примерно 28–30% нынешнего файла в байтах, в зависимости от выбранного домена). Это верхняя оценка экономии только на статическом файле; токены, фактический prompt host-а и денежный эффект не измерены. Реальная экономия зависит от того, как конкретный агент загружает `AGENTS.md` и повторно использует контекст.

| Приоритет | Изменение структуры/формулировок | Ожидаемая польза | Риск / условие |
| --- | --- | --- | --- |
| 1 | Компактный bootstrap: оставить общие запреты, выбор домена/профиля, путь к нужным источникам и правила остановки; подробную сводку загружать только для выбранного домена | Удаляет инструкции по трём нерелевантным доменам в текущей задаче | Нельзя отложить критические общие ограничения; нужен безопасный механизм чтения файлов у host-а |
| 2 | Убрать дублирование: в entrypoint оставить краткую исполняемую выжимку, в доменной политике — полное правило и детали; не копировать туда целые таблицы | Меньше повторного ввода при чтении политик/процессов по задаче | Выжимка не должна противоречить источнику и обязана указывать, где читать норму |
| 3 | Подгружать по задаче только профиль и workflow, затем — нужную схему/решение/пример | Не читать «всё подряд» и уменьшить tool output | Сложные задачи могут требовать нескольких источников; контекст нельзя обрезать до потери доказательств |
| 4 | Переписать длинные абзацы в структуру «условие → действие → исключение/стоп → результат», убрать повторные объяснения и вводные фразы | Умеренная, безопасная экономия без нового механизма | Не сокращать точные обязанности, provenance, ворота и критерии приёмки |

[В] Одна только редактура формулировок, вероятно, даст меньший выигрыш, чем условная загрузка доменных фрагментов; это гипотеза о приоритетах, не измеренный прогноз. Методы «пещерного человека», неясные аббревиатуры и жёсткое «без объяснений» здесь опасны: они могут уменьшить текст, одновременно снизив надёжность соблюдения правил.

[И] `HYAI/core/kernel/**` и `HYAI/core/domains/kit/**` — защищённые зоны; изменения требуют одобрения владельца (`HYAI-PERM-G05`). Поэтому здесь предлагается эксперимент и план, а не незапрошенная правка норм.

### Итоговая оценка

[В] Это полезная подборка эвристик, но не надёжная техническая спецификация и не план внедрения. Самые сильные части — измерять расход, не тащить нерелевантный контекст, ограничивать лишние шаги и оптимизировать выводы инструментов без потери доказательств. Самые слабые — универсальные проценты, устаревающие/непривязанные цены, утверждение про экспоненциальный рост и представление псевдокода как готового решения.

## Варианты

| Вариант | Плюсы | Минусы | Цена | Что ломает |
| --- | --- | --- | --- | --- |
| A. Измерить и спроектировать компактный bootstrap с загрузкой выбранного домена — рекомендация | Самый прямой путь сократить всегда передаваемый текст, не смешивая его с runtime-функциями | Требует понять поведение host-а; изменение ядра/сборщика затрагивает защищённые зоны и нуждается в одобрении владельца | Средняя: baseline, макет двух вариантов, проверки инвариантов и A/B на задачах | Риск пропуска правила, если условная загрузка не сработает; нужен fail-safe путь к полному источнику |
| B. Использовать runtime-советы как необязательный checklist | Можно отдельно применить к тем интеграциям, которые дают доступ к API usage/cache | Не оптимизирует автоматически инструкции HYAI | Низкая: собрать usage/cost baseline и сравнить пилот | Ничего, если советы не становятся безусловными требованиями |
| C. Подготовить нейтральную памятку в существующей документации HYAI | Даст пользователям проверяемый материал с оговорками | Требует отдельной задачи домена `docs`; при выполнении через `kit` нужно явно указать `cross_scope` и решение `KIT-*` | Средняя: редактура, ссылки, проверка примеров и источников | Риск быстро устаревающих API/цен; снизить датированием и провайдер-нейтральной формулировкой |
| D. Встроить управление токенами и моделями в HYAI | Возможны автоматические лимиты/метрики, если продукт действительно контролирует runtime | Меняет границы продукта; потребует runtime, интерфейсов провайдера, тестов и решений по данным | Высокая: проектирование и реализация отдельной подсистемы | Может смешать каркас правил с исполнителем агента и привязать его к провайдерам |

## Рекомендация

[В] Первым шагом выбрать A: сравнить текущую генерацию `AGENTS.md` с макетом, где всегда загружено только ядро-bootstrap, а после выбора домена доступен только соответствующий фрагмент. Не менять нормы до одобрения владельца (`HYAI-PERM-G05`) и не обещать процент экономии: сначала проверить, что host действительно передаёт весь `AGENTS.md`, затем измерить реальные токены и качество на одинаковых задачах. Сохранить fail-safe путь к полным политикам и обязательным ограничениям.

[В] В текущем PR можно обосновать эту архитектуру и benchmark-план; собственно реализация относится к отдельному согласованному изменению защищённых файлов. B и C остаются дополнительными мерами для конкретного runtime или документации, а D — отдельным расширением продукта.

Для проверки реальной экономии сравнивать одинаковый набор задач до/после: входные токены по ответам API (включая cached input, если провайдер сообщает его), стоимость, число вызовов инструментов, задержку, долю успешных задач и повторную работу. Принимать вариант только при сохранении качества и прохождении тестов на маршрутизацию, безопасность, ворота и отчёты. Числа из переданных гайдов использовать как гипотезы, не как гарантии.

## Открытые вопросы

- `[?] Q-KIT-01` — какой host/runtime и provider/model используются, как они загружают `AGENTS.md` и позволяют ли читать доменные файлы по требованию? Без этих данных нельзя оценить, будет ли lazy loading реальным и как измерить его эффект.
- Не проверялись внешние ссылки из обоих текстов и актуальные тарифы провайдеров; этот разбор оценивает содержание и применимость к репозиторию, а не проводит внешнюю факт-проверку.
