# Разбор применимости рекомендаций по токенам к HYAI

## Вопрос

Насколько технически оправданы переданные рекомендации по снижению расхода токенов и что из них применимо к HYAI?

## Разбор

### Краткий вывод

[В] Основа не бредовая: повторная передача длинной истории, избыточные ответы инструментов и ненужная генерация действительно могут повышать расход и задержку. Но текст смешивает контекстное окно, тарифицируемые токены, деньги, задержку и качество; заявления об экспоненциальном росте и процентах экономии не обоснованы данными, приложенными к рекомендациям.

[И] Паспорт описывает HYAI как каркас правил для агента — домены, профили и проверки (`HYAI/meta/project.md`); манифест задаёт entrypoint, конфигурацию и проверки (`HYAI/meta/manifest.yaml`). В изученных источниках нет реализации LLM-runtime, API-провайдера, кэширования запросов, роутинга моделей или оркестратора. Это вывод о данном репозитории, а не утверждение о том, что такие механизмы нельзя реализовать в подключённом пользователем runtime.

### Оценка тезисов

| Тезис | Оценка | Почему / ограничение |
| --- | --- | --- |
| «Каждый шаг повторно передаёт всю историю», рост «по экспоненте» | [В] Частично верно как описание некоторых stateless API; «экспонента» некорректна для обычного добавления сообщений. Размер контекста одного шага обычно растёт примерно линейно по числу шагов, а суммарный ввод за N шагов может расти квадратично, если каждый раз отправлять всю историю. Stateful API, сокращение истории и prompt caching меняют картину и/или тарификацию. |
| Обрезка истории и tool results | [В] Полезно только при сохранении нужных фактов, ошибок, ссылок на источники и возможности дочитать исходник. Наивное усечение по символам способно удалить важный контекст и ухудшить корректность. |
| Sliding window + summary | [В] Практичный шаблон, но приведённый код демонстрационный: summary заменяется новым, а не явно объединяется с предыдущим; фиксированные последние три сообщения могут разорвать пару вызов/ответ инструмента. Нужны тесты сохранения решений, ограничений и provenance. |
| Prompt caching | [В] Потенциально снижает стоимость повторного ввода при поддержке провайдера и выполнении его условий. Не сокращает автоматически размер контекстного окна; hit rate, минимальный префикс, срок жизни и тариф зависят от API. Пример с одним beta-заголовком не универсален. |
| Сжатие system prompt, краткий JSON, жёсткий `max_tokens` | [В] Хорошие рычаги только при неизменной полноте задачи. JSON может быть многословнее свободного текста; лимит обрезает ответ, а не гарантирует экономию, если естественный ответ и так короче. Универсальный запрет на пояснения ухудшает задачи, где нужна проверяемая аргументация. |
| Дешёвая модель, иерархия агентов, speculative execution | [В] Может быть выгодно при измеренной разнице качества и цене. Дополнительная классификация, критика, синтез и повторные запросы сами стоят денег и времени; декомпозиция может дублировать контекст. Проверка ответа другой LLM не равна проверке по эталону. |
| State machine и лимиты шагов | [В] Хорошо ограничивают известный стабильный процесс, но способны преждевременно оборвать исследование или восстановление после ошибки. Нужны условия завершения, обработка сбоя и путь эскалации. |
| Кэш результатов инструментов | [В] Может сэкономить повторное выполнение детерминированного инструмента. Сам по себе кэш не сокращает токены, если сохранённый полный результат снова передаётся модели; для изменяемых данных нужны срок годности и инвалидирование. |
| TOON, RTK/Tokenade, LLMLingua | [Г] Возможная экономия зависит от токенизатора, структуры данных, качества восстановления и конкретной задачи; проценты из текста здесь не подтверждены тестом на целевом корпусе. Установка прокси/библиотек добавляет эксплуатационные, безопасностные и приватностные издержки. |
| Цены и числа экономии (−20–90%, «80/20», $/M) | [В] Это не переносимые константы: стоимость зависит от провайдера, модели, типа токена, кэширования, тарифа и даты. В переданных текстах нет воспроизводимого baseline, трасс запросов, состава задач и измерения качества, поэтому проценты не подтверждены. |
| Мониторинг токенов и стоимости | [В] Направление правильное, но пример формулы с фиксированными тарифами — иллюстрация, не актуальный калькулятор. Нужно отдельно учитывать uncached/cached input, output и иные тарифицируемые категории, если API их сообщает; сравнивать стоимость успешной задачи, качество и повторы. |

**Примечания к псевдокоду.** [В] В примере `speculative_solve` проверка `"YES" in check` может принять ответ вроде `NO — YES не подтверждено`; нужен строгий формат результата, а лучше проверяемый критерий. В примере token budget оценка `estimated` плюс `usage.total_tokens` может дважды учесть ввод, если `total_tokens` уже включает его. `len(solution) // 3` — лимит в символах, а не оценка токенов. В примере кэширования `md5` не нужен как криптографическая защита ключа и не решает проблемы устаревания данных. Это иллюстративные фрагменты, не готовая production-реализация.

### Применимость к HYAI

[И] У HYAI есть короткий entrypoint и сборка инструкций, доменные процессы, отчёты как переносимое состояние между сессиями и проверки (`HYAI/core/kernel/agents.md`, `HYAI/core/kernel/workflows/task.md`, `HYAI/meta/reports/README.md`). Это поддерживает выборочное чтение и передачу компактного состояния на уровне практики, но не управляет API-историей, tool schemas, prompt cache, модельным роутингом или `max_tokens`.

| Направление | Применимость | Практический вывод |
| --- | --- | --- |
| Минимизировать нерелевантное чтение; кратко фиксировать результат и открытые вопросы | Высокая, как рабочая рекомендация пользователю HYAI | Совместимо с текущими процессами и отчётами; не обещать конкретный процент экономии. |
| Фильтрация вывода инструментов, бюджет шагов, ограничения генерации | Частичная | Имеет смысл формулировать как советы для runtime/интеграции с явными оговорками о потере данных и проверке полноты. |
| Prompt caching, sliding-window на уровне API, роутинг, Batch API, multi-agent orchestration | Низкая на уровне самого каркаса | Реализуются в конкретном хосте/провайдере, которых HYAI не задаёт. Не превращать в обязательные правила ядра. |
| Внешние утилиты, прокси и компрессоры | Условная | Сначала benchmark и анализ данных/приватности; зависимости требуют отдельной цели и проверки. |
| Проценты экономии и универсальные тарифы | Не переносить | Требовать benchmark: модель/провайдер/версия, набор задач, baseline, качество, стоимость и задержка до/после. |

### Итоговая оценка

[В] Это полезная подборка эвристик, но не надёжная техническая спецификация и не план внедрения. Самые сильные части — измерять расход, не тащить нерелевантный контекст, ограничивать лишние шаги и оптимизировать выводы инструментов без потери доказательств. Самые слабые — универсальные проценты, устаревающие/непривязанные цены, утверждение про экспоненциальный рост и представление псевдокода как готового решения.

## Варианты

| Вариант | Плюсы | Минусы | Цена | Что ломает |
| --- | --- | --- | --- | --- |
| A. Использовать как необязательный checklist для конкретного runtime — рекомендация | Быстрый и обратимый путь; позволяет выбрать применимые меры по измерениям | Нужны данные конкретной интеграции для оценки выгоды | Низкая: собрать usage/cost baseline и сравнить пилот | Ничего, если советы не становятся безусловными требованиями |
| B. Подготовить нейтральную памятку в существующей документации HYAI | Даст пользователям практический, проверяемый материал с оговорками | Требует отдельной задачи домена `docs`; при выполнении через `kit` нужно явно указать `cross_scope` и решение `KIT-*` | Средняя: редактура, ссылки, проверка примеров и источников | Риск быстро устаревающих API/цен; снизить датированием и провайдер-нейтральной формулировкой |
| C. Встроить управление токенами и моделями в HYAI | Возможны автоматические лимиты/метрики, если продукт действительно контролирует runtime | Меняет границы продукта; потребует runtime, интерфейсов провайдера, тестов и решений по данным | Высокая: проектирование и реализация отдельной подсистемы | Может смешать каркас правил с исполнителем агента и привязать его к провайдерам |

## Рекомендация

[В] Выбрать A сейчас; не переносить руководство целиком в ядро и не создавать новый домен: предмет не требует отдельной нормативной базы/системы доступа, а рекомендации относятся к runtime, который HYAI не контролирует. Если понадобится материал для пользователей, отдельно поручить B существующему домену `docs`, после первичной проверки ссылок и примеров. C рассматривать только при явном решении расширить HYAI от каркаса правил к runtime.

Для проверки реальной экономии сравнивать одинаковый набор задач до/после: input/output/cached tokens и стоимость по ответам API; число вызовов инструментов; задержку; долю успешных задач и повторную работу. Изменение принимать только если экономия подтверждается без падения качества. Числа из переданных гайдов использовать как гипотезы, не как ожидаемые гарантии.
