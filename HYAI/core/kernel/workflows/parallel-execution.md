# `parallel-execution` — диспетчеризация независимых задач

Применяется, если агентское окружение умеет запускать несколько процессов или задач конкурентно (`HYAI-INT-30`). Само наличие возможности не отменяет проверку прав, лимитов и зависимости данных.

## Порядок

1. **Проверить среду при входе.** До выбора домена/профиля установить, доступны ли запуск процессов, конкурентные вызовы и механизм получения их результатов. Если нет — зафиксировать неприменимость параллельной части и работать последовательно.
2. **Разложить граф задач.** Отметить входы, результаты и зависимости. Все независимые разрешённые задачи запускай одновременно в пределах согласованного лимита; последовательность обязательна при зависимости результата, общей изменяемой области, гонке записи или запрете доступа.
3. **Согласовать предел.** До первого конкурентного запуска спросить пользователя о максимуме одновременно выполняемых задач/процессов. Если он заранее назван — зафиксировать; если пользователь делегирует выбор агенту — объявить выбранный консервативный предел. Не отправлять задачи, пока лимит не определён, и не превышать его.
4. **Поставить удалённые задачи в очередь.** Для MCP, API сервисов и API моделей организовать очередь с исполняющим диспетчером, уникальным ID и состоянием задания (`queued`, `running`, `succeeded`, `failed`, `cancelled`). Сохранять результат или ошибку, связь с входной задачей и требуемое действие после завершения. Применять поддерживаемые идемпотентность, timeout, retry и rate limits; не повторять платный/неидемпотентный вызов вслепую.
5. **Получать завершения без ожидания всей группы.** Предпочитать простой callback; если он недоступен, использовать события, уведомления MCP либо неблокирующее получение статуса. Обрабатывать каждый готовый результат сразу, когда его зависимости закрыты; не блокировать агента ожиданием других независимых заданий. Не создавать busy loop частым polling.
6. **Продолжать по графу.** После каждого результата проверять ошибки и зависимости, ставить готовые независимые этапы в очередь в пределах лимита, а зависимые запускать только после необходимых входов. После завершения группы сверить, что каждое задание имеет конечное состояние и результат сообщён пользователю.
7. **Выбрать простейшую реализуемую технологию.** Использовать то, что можно развернуть в текущем агентском окружении: встроенный диспетчер/асинхронный API предпочтительнее нового сервиса; отдельную очередь или callback-сервис создавать только если это нужно и допустимо. Технология не предписана. Учитывать `HYAI-PERM-N02..04`, сетевые allowlist, контуры данных, стоимость, квоты и доступ.
8. **Остановить безопасно при ограничении.** Если очередь/уведомления недоступны, параллельность запрещена или лимит не согласован — не имитировать асинхронность; продолжить безопасным последовательным способом либо сообщить, что именно блокирует задачу.

## Критерий готовности

Каждая независимая допустимая задача была запущена конкурентно в пределах явно известного лимита; удалённые задания отслежены до конечного состояния; готовые результаты обработаны без ожидания не связанных с ними заданий; ограничения среды, ошибки и непринятые результаты названы явно.
