# Идентификаторы правил

Идентификатор правила — это адрес, а не украшение. По нему ссылаются политики, отчёты, движки и отказы агента. Поэтому он отвечает на три вопроса сразу: **кто владеет правилом**, **о каком классе речь** и **какой это номер**.

## 1. Формат

```
<OWNER>-<CLASS>-<NN>            пример: HYAI-ART-15
<OWNER>-<CLASS>-<ПОДКЛАСС><NN>  пример: HYAI-PERM-N01 — класс `PERM-N`, номер `01`
<OWNER>-<CLASS>-<NN>.<NN>       не используется: диапазоны пишутся «HYAI-INT-01..30»
```

Два вида существуют потому, что у запретов и ворот ядра класс двухчастный: `PERM-N` (неотменяемые), `PERM-G` (ворота), `PERM-A`, `PERM-P`, `PERM-E`, `PERM-V`. Буква подкласса приклеена к номеру без дефиса: `HYAI-PERM-N01`, а разделять её дефисом нельзя. Разбор: владелец — до первого дефиса, класс — до последнего, номер — последние два знака; если первый из них буква, а пара «класс-буква» объявлена в реестре, это двухчастный класс, и номер — две цифры после буквы.

| Часть | Что означает | Примеры |
| --- | --- | --- |
| `OWNER` | чей это закон: каркаса, домена или проекта | `HYAI`, `KIT`, `SW`, `DOC`, `NR`, `PRJ` |
| `CLASS` | вид правила внутри владельца | `PERM`, `INT`, `ART`, `DEC`, `PROV`, `POL`, `TXT`, `CMP`, `ENT`, `EXP`, `READ` |
| `NN` | двузначный номер, неизменный навсегда | `01`, `28` |

Диапазон пишется через `..`: `HYAI-INT-01..30`. Перечисление — через запятую внутри одного обрамления.

## 2. Владельцы (`OWNER`)

| Код | Кто владеет | Где живёт | Кто меняет |
| --- | --- | --- | --- |
| `HYAI` | каркас: правила, действующие в любом домене | `HYAI/core/kernel/policies/*.md` | только владелец (`HYAI-PERM-G05`) |
| `KIT` | домен, который расширяет сам каркас | `HYAI/core/domains/kit/policy.md` | владелец |
| `SW` | домен `software` | `HYAI/core/domains/software/policy.md` | домен |
| `DOC` | домен `docs` | `HYAI/core/domains/docs/policy.md`, `text.md` | домен |
| `NR` | домен `narrative` | `HYAI/core/domains/narrative/*.md` | домен |
| `PRJ` | **этот проект**: правила, которых нет в каркасе | `HYAI/meta/policies/*.md` | проект |

`PRJ` существует ровно для одного случая: проект вводит ограничение, которого нет в каркасе (например, «все миграции только через `alembic`»). Такое правило живёт в `HYAI/meta/policies/`, а не в домене: домен переносим, проект — нет.

Домен, добавленный проектом (например, `legal`), берёт свой `OWNER` из `metadata.name` домена в верхнем регистре и регистрируется в реестре (§5). Прежде чем вводить новый код — проверить реестр: два владельца с одним кодом ломают адресацию.

## 3. Классы (`CLASS`)

Классы ядра:

| Класс | Что | Файл |
| --- | --- | --- |
| `PERM-N` | неотменяемые запреты | `permissions.md` |
| `PERM-G` | ворота: действие требует одобрения | `permissions.md` |
| `PERM-A` | умолчания: как делать, если не сказано иное | `permissions.md` |
| `PERM-P` | протокол одобрения: что предъявить и как зафиксировать | `permissions.md` |
| `PERM-E` | гигиена исполнения: как не сломать среду и данные | `permissions.md` |
| `PERM-V` | git и ветки | `permissions.md` |
| `INT` | взаимодействие с пользователем, вход и координация исполнения | `interaction.md` |
| `ART` | артефакты, отчёты, индексы, история | `artifacts.md` |
| `DEC` | решения | `decisions.md` |
| `PROV` | провенанс и маркеры | `provenance.md` |

Классы доменов задаёт сам домен; общие для всех (регистрируются в реестре для каждого владельца):

| Класс | Что |
| --- | --- |
| `POL` | правила домена по умолчанию (если не нужен свой класс) |
| `TXT` | чистка и форма текста |
| `ENT` | создание и проверка сущностей |
| `CMP` | компетенция и уровни |
| `EXP` | выгрузка и публикация |
| `READ` | что и когда читать |
| `INV` | инвариант структуры, проверяемый движком |

Один класс — один предмет. Если правило не помещается в класс, это не повод завести `MISC`: значит, либо правило принадлежит другому владельцу, либо предмета ещё нет и его надо назвать.

**Номер без класса — дефект, а не сокращение.** Запись вида `NR-<NN>` не разбирается как ID, поэтому правило молча выпадает из учёта, а ссылка на него не проверяется. Первый выпуск HYAI так и писал; при переходе на эту схему все такие номера переименованы (`NR-01..14` → `NR-POL-01..14`), а `check_rules.py` теперь ловит формат `<OWNER>-NN` отдельной ошибкой. Строка миграции «старый → новый» разрешена: в ней назван новый ID.

## 4. Номер

1. **Номер не переиспользуется.** Удалённое правило оставляет номер занятым навсегда (`HYAI-DEC-07` оригинала, теперь `HYAI-DEC-17`): иначе старые ссылки начнут врать.
2. **Номер не меняет смысл.** Если смысл правила изменился настолько, что старые ссылки вводят в заблуждение, — новое правило с новым номером и полем `supersedes`.
3. **Сквозная нумерация внутри владельца и класса.** `HYAI-PERM-G01..G10`, затем следующие ворота — `G11`, даже если `G05` удалён.
4. **Разрывы нормальны.** Пропуск в нумерации означает «правило было и ушло», а не «забыли».
5. **Двузначность.** `G01`, не `G1`. Трёхзначность допустима только при честном превышении 99 правил в классе.
6. **Решения ≠ правила.** Решение — `<PREFIX>-NNNN` (четыре знака), правило — `<OWNER>-<CLASS>-NN` (два). Префикс области (`P`, `SW`, `NR`) и владелец правила (`HYAI`, `SW`, `NR`) — разные пространства: `SW-0007` и `SW-POL-07` не конфликтуют.

## 5. Реестр

Машинная часть схемы — [`HYAI/meta/schema/rule-ids.yaml`](../../../meta/schema/rule-ids.yaml): владельцы, классы, вышедшие из обращения номера. Проверка — [`HYAI/tools/check_rules.py`](../../../tools/check_rules.py):

| Что проверяется | Нарушение |
| --- | --- |
| Все определённые ID соответствуют формату | `HYAI-PERM-N01` без владельца — ошибка формата |
| Владелец и класс зарегистрированы | неизвестный `OWNER` или `CLASS` |
| ID определён ровно один раз | два определения одного ID в разных файлах |
| Каждая ссылка указывает на определённый ID | ссылка на правило, которого нет |
| Вышедший из обращения ID не используется как действующий | правило в `retired` упомянуто без пометки |
| Номер без класса не встречается (`NR-<NN>`) | формат первого выпуска; правило выпало бы из учёта |
| Номер не переиспользован после смены смысла | ID есть и в `retired`, и в политике как действующее |

Реестр `retired` — это память каркаса (74 записи: 20 правил ядра без префикса владельца и 54 правила доменов без класса): там указано, что было под номером, почему ушло и чем заменено. Без него следующая сессия снова займёт `HYAI-PERM-G02` «настоящим» смыслом — ровно та ошибка, которую эта схема и лечит.

## 6. Как добавить правило

1. Найти владельца: правило действует везде (`HYAI`), в домене (`SW`/`DOC`/`NR`/`KIT`) или только в этом проекте (`PRJ`).
2. Выбрать класс. Если подходящего нет — назвать новый класс и добавить его в [`rule-ids.yaml`](../../../meta/schema/rule-ids.yaml), а не в код.
3. Взять следующий свободный номер: максимальный действующий + 1, с учётом `retired` и `superseded`.
4. Записать правило одной строкой: ID, формулировка в повелительном наклонении, чем проверяется.
5. Если правило проверяемо автоматически — добавить проверку и в неё сослаться этим же ID (`reason` в `HYAI/meta/lint/terms/*.json`, ветка движка или тест).
6. Прогнать `python3 HYAI/tools/check_rules.py`.

## 7. Чего не делать

| Антипаттерн | Почему плохо |
| --- | --- |
| `HYAI-PERM-G02` с новым смыслом | старая ссылка начинает врать — это уже случалось |
| Один ID на два правила | адрес перестаёт быть адресом |
| Правило без класса (`REQUEST-1`) | непонятно, кто владелец и что с ним делать |
| Правило домена в ядре | ядро перестаёт быть переносимым |
| Правило проекта в домене | при обновлении `HYAI/core` правило уедет вместе с ним |
| Номер «на вырост» | разрыв в нумерации скрывает историю |
