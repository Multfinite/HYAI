# UML 2.5: регламент 14 диаграмм

Документ отвечает на вопрос «как сделать диаграмму так, чтобы её можно было проверить».
Источник правил — [`policy.md`](policy.md): базовые `DOC-POL-10..12`, общие `DOC-POL-16..20`
и правила типов `DOC-POL-21..34`. Пошаговые процессы лежат в
[`workflows/README.md`](workflows/README.md); общая активация — навык `uml`.

## 1. Общий регламент

Любая из 14 диаграмм делается по одному и тому же каркасу. Тип меняется, каркас — нет.

| Шаг | Что делать | Критерий |
| --- | --- | --- |
| 1. Вопрос | Сформулировать один вопрос, на который ответит схема | Ответ «всё сразу» → схема не нужна (`DOC-POL-11`) |
| 2. Тип | Выбрать один из 14 типов по таблице ниже | Тип не подменяется ER, C4 или BPMN без решения `DOC-*` |
| 3. Источник | Указать файл и строку/раздел-источник | Схема строится не по памяти (`DOC-POL-17`) |
| 4. Нотация | PlantUML или Mermaid, файл рядом с документом | Текст, не только картинка (`DOC-POL-19`) |
| 5. Шапка | ID, вопрос, читатель, тип, нотация, источник, дата среза | Заполнены все поля (`DOC-POL-18`) |
| 6. Элементы | Добавить только то, что отвечает на вопрос | Лишний элемент удаляется (`DOC-POL-20`) |
| 7. Связи | Подписать связи, указать кратность где применимо | Подписи есть, стрелки не висят |
| 8. Проверка | Рендер, сверка с источником, удаление шума | Расхождение → `Q-*`, не тихая правка |
| 9. Публикация | Картинка — выгрузка рядом, правка — в текст | Источник остаётся текстовым |

## 2. Структурные диаграммы

### DOC-POL-21 — Диаграмма классов

**Вопрос:** какие типы есть в модели, какие у них атрибуты и операции и как они связаны.
**Источник:** сигнатуры классов/структур в коде, контракт модуля или утверждённая спецификация.
**Элементы:** класс, интерфейс, абстрактный класс, перечисление; атрибуты и операции с видимостью (`+`, `-`, `#`); кратность ассоциаций.
**Связи:** ассоциация с меткой и кратностью, наследование, реализация, агрегация/композиция, зависимость.
**Ошибки:** подмена ER-диаграммой, классы без атрибутов, стрелки без подписей, копирование всего кода подряд.
**Проверка:** каждый класс найден в источнике; каждая связь прочитана как предложение; лишние классы убраны.

### DOC-POL-22 — Диаграмма компонентов

**Вопрос:** из каких компонентов собрана система и через какие интерфейсы они общаются.
**Источник:** манифест сборки, конфигурация модулей, контракты API.
**Элементы:** компонент, предоставляемый интерфейс (шар), требуемый интерфейс (гнездо), порт, артефакт.
**Связи:** делегирование, зависимость, сборка «provided → required».
**Ошибки:** компонент равен одному файлу, интерфейсы без описания, смешивание компонентов с классами.
**Проверка:** границы компонента совпадают с единицей поставки; каждый интерфейс имеет контракт в источнике.

### DOC-POL-23 — Диаграмма развёртывания

**Вопрос:** куда именно разворачиваются артефакты и в каком окружении работают.
**Источник:** инфраструктурный манифест, Dockerfile, конфигурация окружений, реестр версий.
**Элементы:** узел (устройство или среда исполнения), артефакт, связь развёртывания, стереотипы окружения.
**Связи:** «артефакт → узел», коммуникация между узлами с указанием протокола.
**Ошибки:** выдуманные адреса и версии, сеть «на глаз», смешивание логических и физических узлов.
**Проверка:** узел и артефакт сверены с манифестом; версия указана; расхождение → `Q-*`.

### DOC-POL-24 — Диаграмма объектов

**Вопрос:** как выглядит конкретное состояние системы в заданный момент.
**Источник:** тестовые фикстуры, снимок состояния, лог или пример из спецификации.
**Элементы:** объект с именем и значениями атрибутов, ссылка на класс-тип; снимок ограничен моментом времени.
**Связи:** связи объектов с кратностью и метками; показываются только существующие в момент среза.
**Ошибки:** дублирование определений классов, отсутствие времени среза, несуществующие значения.
**Проверка:** снимок воспроизводится из фикстуры; время среза указано в шапке.

### DOC-POL-25 — Диаграмма пакетов

**Вопрос:** как сгруппированы элементы и какие пакеты от каких зависят.
**Источник:** каталоги проекта, пространство имён, матрица зависимостей сборки.
**Элементы:** пакет, вложенные пакеты, видимость элементов (`+`, `#`, `-`).
**Связи:** зависимость между пакетами, импорт, обобщение.
**Ошибки:** пакет как «слой C4», циклические зависимости, пакеты без элементов.
**Проверка:** каждая группа пакетов совпадает с каталогом или пространством имён; циклы отсутствуют.

### DOC-POL-26 — Диаграмма профилей

**Вопрос:** какие стереотипы и ограничения применяются к модели и где профиль использован.
**Источник:** решение `DOC-*`, схема метамодели, конфигурация инструмента моделирования.
**Элементы:** профиль, стереотип, метакласс, ограничение (OCL или текст), расширение (`extend`).
**Связи:** применение профиля (`profile application`) к пакету или модели.
**Ошибки:** стереотип без метакласса, новый стереотип без решения, смешивание с обычным классом.
**Проверка:** каждый стереотип имеет метакласс и ограничение; применение профиля показано явно.

### DOC-POL-27 — Диаграмма композитной структуры

**Вопрос:** как именно устроен классификатор изнутри — из каких частей и портов он состоит.
**Источник:** реализация класса/компонента, контракт внутренних ролей.
**Элементы:** классификатор-владелец, часть с ролью и кратностью, порт, коннектор.
**Связи:** коннекторы между частями и портами, делегирование на внешние интерфейсы.
**Ошибки:** дублирование диаграммы классов, части без ролей, порты без типов.
**Проверка:** каждая часть найдена в коде; каждый порт имеет тип; классовая диаграмма не повторяется.

## 3. Диаграммы поведения

### DOC-POL-28 — Диаграмма активности

**Вопрос:** в каком порядке выполняется работа, где ветвления и кто за что отвечает.
**Источник:** сценарий use case, код потока управления, описание бизнес-процесса.
**Элементы:** действие, решение, слияние, раздвоение/соединение, начальная и конечная точки, дорожки (swimlanes).
**Связи:** поток управления с метками условий; поток объектов где важен передаваемый данные.
**Ошибки:** подмена BPMN без причины, отсутствие дорожек при нескольких исполнителях, петли без условия выхода.
**Проверка:** каждый переход возможен; условия взаимно исключают друг друга; дорожки соответствуют ролям из источника.

### DOC-POL-29 — Диаграмма вариантов использования

**Вопрос:** кто и зачем взаимодействует с системой и где её граница.
**Источник:** ТЗ, интервью, список требований с `REQ-ID`.
**Элементы:** актор, вариант использования, граница системы, пакет вариантов.
**Связи:** ассоциация «актор — вариант», `include`, `extend`, обобщение акторов и вариантов.
**Ошибки:** варианты как функции, текст сценария внутри овала, размытая граница системы.
**Проверка:** каждый вариант имеет `REQ-ID` и текст сценария в документе; граница нарисована.

### DOC-POL-30 — Диаграмма состояний

**Вопрос:** какие состояния проходит объект и по каким событиям переходит между ними.
**Источник:** конечный автомат в коде, контракт сущности, спецификация протокола.
**Элементы:** состояние, начальное/конечное состояние, вложенные состояния, history-псевдосостояние.
**Связи:** переход с меткой «событие [условие] / действие», составные переходы.
**Ошибки:** подмена активностью, переходы без событий, состояния без описания.
**Проверка:** каждый переход соответствует событию в источнике; тупиковых состояний нет, кроме конечных.

### DOC-POL-31 — Диаграмма последовательности

**Вопрос:** кто кому и в каком порядке отправляет сообщения.
**Источник:** трассировка вызовов, контракт API, сценарий use case.
**Элементы:** линии жизни, активации, сообщения (синхронные/асинхронные), комментарии.
**Связи:** вызовы по времени сверху вниз; фрагменты `alt`, `opt`, `loop`, `par`, `break`.
**Ошибки:** перепутанный порядок, сообщения без получателя, фрагменты безусловия.
**Проверка:** порядок совпадает с трассировкой; каждый фрагмент имеет условие и границы.

### DOC-POL-32 — Диаграмма коммуникации

**Вопрос:** кто с кем связан и какие сообщения идут по этим связям.
**Источник:** граф вызовов, конфигурация связей объектов, та же трассировка, что и для sequence.
**Элементы:** объекты, связи, составные сообщения, стереотипы ссылок.
**Связи:** нумерованные сообщения (1, 1.1, 2) с меткой и направлением; порядок задаётся номером.
**Ошибки:** попытка показать время стрелками, числа без порядка, дублирование sequence без пользы.
**Проверка:** номера сообщений согласованы с порядком в трассировке; каждый объект есть в источнике.

### DOC-POL-33 — Диаграмма тайминга

**Вопрос:** как состояния или значения меняются в реальном времени.
**Источник:** спецификация, протокол тестирования, метрики, тайминговые требования с `REQ-ID`.
**Элементы:** шкала времени с tick-метками, линии состояний/значений, пороги, состояния в интервалах.
**Связи:** переходы по времени с указанием длительности и условия.
**Ошибки:** отсутствие масштаба времени, состояния без значений, подмена sequence.
**Проверка:** каждый интервал имеет начало и конец; пороги сверены с требованием.

### DOC-POL-34 — Диаграмма обзора взаимодействий

**Вопрос:** в каком порядке выполняются фрагменты взаимодействий и каковы точки ветвления.
**Источник:** сценарий верхнего уровня, набор sequence-диаграмм, контракт оркестратора.
**Элементы:** фрагмент взаимодействия (ссылка на sequence), действие, решение, начальная/конечная точка, дорожки.
**Связи:** поток управления между фрагментами; ссылка на отдельную диаграмму последовательности.
**Ошибки:** внутреннее содержимое sequence вставлено целиком, фрагмент без ссылки, ветвления без условия.
**Проверка:** каждый фрагмент указывает на свою sequence-диаграмму; поток не имеет тупиков.

## 4. Проверка перед публикацией

1. Рендер проходит без ошибок нотации.
2. Шапка заполнена, источник указан путём.
3. Каждый элемент отвечает на вопрос из шапки; лишние удалены.
4. Связи подписаны, кратность и условия указаны там, где это нужно типу.
5. Расхождения с источником записаны как `Q-*`, а не спрятаны в схему.
6. Картинка, если нужна, выгружена рядом; редактируется текст.
