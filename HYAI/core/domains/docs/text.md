# Чистка текста в `docs`

Правила для ТЗ, спецификаций, руководств, README и комментариев в коде. Применяются в процессе [`../../kernel/workflows/doc-cleanup.md`](../../kernel/workflows/doc-cleanup.md).

**Чем это отличается от `narrative`.** В документе нет «вайба», который нужно защищать: здесь защищают **требование**. Текст без требования — вода, даже если он красиво написан. Голос автора не сохраняется; сохраняется формулировка нормы, число, пример и цитата.

## 1. Требование прежде текста

`DOC-TXT-01`. **Нет требования — нет строки.** Абзац, из которого нельзя вывести проверяемое утверждение или нужный читателю факт, удаляется.
`DOC-TXT-02`. **Норму не пересказывают.** Определение, данное в `policy.md` или спецификации, повторяется ссылкой (`DOC-POL-09`), а не вторым текстом: две формулировки одной нормы расходятся.
`DOC-TXT-03`. **Формулировка нормы неприкосновенна.** Чистка не меняет смысл требования, его ID, число, единицу измерения и условие применимости. Изменился смысл — это не чистка, а правка нормы с решением (`HYAI-PERM-G01`).

## 2. Вода

`DOC-TXT-04`. **Вводные и оценочные обороты удаляются.** «Как известно», «важно отметить», «в современном мире», «не секрет, что», «стоит подчеркнуть» — занимают место и не несут требования.
`DOC-TXT-05`. **Не защищаться от воображаемого читателя.** «Это не значит, что…», «вопреки распространённому мнению» — только если рядом лежит реальное заблуждение, зафиксированное как `[?]` или дефект.
`DOC-TXT-06`. **Не описывать документ.** «В этом разделе…», «как видно из таблицы», «ниже приведён список» — мета-комментарий; читатель видит структуру сам.
`DOC-TXT-07`. **Не объяснять очевидное следствие.** Если вывод следует из предыдущего абзаца, он удаляется: остаётся факт, из которого он следует.
`DOC-TXT-08`. **Дубли заменяются ссылкой.** Повтор правила, примера или таблицы в другом документе — ошибка: одна норма живёт в одном месте (`DOC-POL-09`).

## 3. Читатель и пример

`DOC-TXT-09`. **Читатель назван, вопрос задан с первой строки.** Документ начинается с ответа на вопрос читателя, а не с истории вопроса и не с общего введения.
`DOC-TXT-10`. **Пример важнее описания.** Рабочий фрагмент, команда или схема, которую можно скопировать и выполнить; пример без вывода/результата — половина примера.
`DOC-TXT-11`. **Форма по данным.** Однородные данные — таблица; причина и цена — абзац; последовательность шагов — нумерованный список. Таблица из одного столбца, список из одной строки и абзац-перечисление — дефект формы.
`DOC-TXT-12`. **Бюджет объёма.** README каталога — до 80 строк, политика — до 300, шаблон — до 120, решение — 120 (`HYAI-DEC-11`). Превышение — сигнал, что документ описывает больше одной темы (`DOC-POL-09`).

## 4. Код и комментарии

`DOC-TXT-13`. **Комментарий объясняет «почему»** и не пересказывает код (`DOC-POL-13`). Комментарий, который врёт после рефакторинга, хуже отсутствующего.
`DOC-TXT-14`. **Ссылка на код — с путём и строкой** (`DOC-POL-08`); ссылка без строки проверяется только на существование файла и устаревает молча.

## 5. Проверки

| --- | --- |
| Вода и оценочные обороты | `lint_terms.py --domain docs` (`doc.no-water`) |
| `TODO` без владельца | `lint_terms.py --domain docs` (`doc.todo-without-owner`) |
| Схема только картинкой | `lint_terms.py --domain docs` (`doc.diagram-as-image-only`) |
| Потеря требований | список ID требований до/после в отчёте |
| Объём | `wc -l` против бюджета |
