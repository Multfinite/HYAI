# Индекс правил домена

Полный текст — [`policy.md`](../../../../HYAI/core/domains/docs/policy.md).

| Правило | Начало |
| --- | --- |
| `DOC-POL-01` | ТЗ и спецификация содержат проверяемые требования: каждое можно проверить тестом, осмотром или измерением. |
| `DOC-POL-02` | Требование имеет идентификатор (REQ-01), источник ([А]/[И]) и критерий приёмки. |
| `DOC-POL-03` | Документ не выдумывает поведение системы. |
| `DOC-POL-04` | Документ пишется для названного читателя (инженер, интегратор, пользователь, оператор) и отвечает на его вопрос с первой строки. |
| `DOC-POL-05` | Пример важнее описания: рабочий фрагмент, команда или схема, которые можно скопировать и выполнить. |
| `DOC-POL-06` | Water-фразы («как известно», «важно отметить», «в современном мире») удаляются: они занимают место и не несут требования. |
| `DOC-POL-07` | Документ не противоречит коду молча: расхождение фиксируется как Q-* или как дефект, с указанием, что считать верным. |
| `DOC-POL-08` | Ссылка на код — с путём и строкой (../src/auth.py#L42); такая ссылка проверяется check_links.py, поэтому устаревшая ссылка видна сразу. |
| `DOC-POL-09` | Один документ — одна тема. |
| `DOC-POL-10` | Диаграмма хранится текстом (Mermaid, PlantUML, Graphviz, D2), чтобы её можно было читать и диффить (HaRD). |
| `DOC-POL-11` | Диаграмма отвечает на один вопрос и подписывает связи. |
| `DOC-POL-12` | Диаграмма не заменяет текст: она объясняет структуру, а требования и правила остаются словами. |
| `DOC-POL-16` | Тип диаграммы выбирается из 14 типов UML 2.5 по названному вопросу; новый тип не изобретается и не подменяется чужим (ER, C4, BPMN) без решения DOC-*. |
| `DOC-POL-17` | Диаграмма строится по источнику — код, документ или требование с путём; только по памяти не строится. |
| `DOC-POL-18` | В шапке текстового файла фиксируются: ID диаграммы, вопрос, читатель, тип, нотация, источник и дата среза/эпоха. |
| `DOC-POL-19` | Диаграмма хранится текстом (PlantUML, Mermaid), элементы и связи подписаны; растр или SVG — выгрузка рядом, но не источник (DOC-POL-10). |
| `DOC-POL-20` | Перед публикацией схема рендерится, сверяется с источником и очищается от элементов, не отвечающих на вопрос; сокращения нотации и нестандартные допущения фиксируются… |
| `DOC-POL-21` | Диаграмма классов описывает типы, атрибуты, операции, видимость и кратность связей; не подменяется ER-диаграммой и не дублирует код без пользы. |
| `DOC-POL-22` | Диаграмма компонентов показывает компоненты, предоставляемые и требуемые интерфейсы, зависимости; границы компонента совпадают с единицей сборки или модуля. |
| `DOC-POL-23` | Диаграмма развёртывания фиксирует узлы, артефакты и связи развёртывания с указанием окружения и версий; сеть и параметры узлов не описываются «на глаз». |
| `DOC-POL-24` | Диаграмма объектов — снимок состояния в момент времени: объекты со значениями и связи между ними; определения классов на ней не повторяются. |
| `DOC-POL-25` | Диаграмма пакетов группирует элементы и показывает видимость и зависимости пакетов; слои C4 и реальные каталоги не смешиваются. |
| `DOC-POL-26` | Диаграмма профилей описывает стереотипы, метаклассы и ограничения с указанием применённого профиля; новый стереотип требует решения DOC-*. |
| `DOC-POL-27` | Диаграмма композитной структуры показывает внутреннее устройство классификатора: части, порты и коннекторы; она не дублирует диаграмму классов. |
| `DOC-POL-28` | Диаграмма активности menunjukkan поток управления, действия, ветвления, слияния и дорожки ответственности; подмена BPMN без причины запрещена. |
| `DOC-POL-29` | Диаграмма вариантов использования показывает акторов, варианты и связи include/extend/обобщения с границей системы; текст сценариев остаётся в документе. |
| `DOC-POL-30` | Диаграмма состояний описывает состояния, переходы, события, условия и действия с вложенностью; она не подменяет диаграмму активности. |
| `DOC-POL-31` | Диаграмма последовательности задаёт линии жизни, сообщения в порядке времени, активации и фрагменты alt/opt/loop/par; порядок определяет смысл. |
| `DOC-POL-32` | Диаграмма коммуникации показывает объекты, связи и нумерованные сообщения; акцент на топологии, а не на времени. |
| `DOC-POL-33` | Диаграмма тайминга задаёт шкалу времени, состояния или значения и переходы по времени; применяется для систем реального времени. |
| `DOC-POL-34` | Диаграмма обзора взаимодействий объединяет фрагменты взаимодействий и поток между ними в стиле активности; вложенная последовательность не дублируется целиком. |
| `DOC-POL-13` | Комментарий объясняет почему, а не что. # увеличиваем таймаут, потому что upstream отвечает за 8 секунд при холодном старте — комментарий; # ставим таймаут — шум. |
| `DOC-POL-14` | Комментарий не является источником истины (SW-POL-01): договорённость живёт в документе или решении, комментарий ссылается на них. |
| `DOC-POL-15` | Чистка документов идёт по отдельным правилам домена — text.md (DOC-TXT-01..14): удаляется вода, сохраняются требование, число, пример и ID. |
